# 劳动维权咨询 Agent —— 作品集演示项目

面向 **AI Agent 应用开发**的完整演示：同一劳动法咨询业务的**四种实现对照**——手写 ReAct 循环版（v1）、LangGraph 编排版（v2）、LangGraph + 跨进程记忆 + 人在环审批版（v3）、流水线基线版；外加**可自动验证的 Agent 评测**与**可观测性/成本核算**。

> **与毕业论文的配套关系**：论文系统（thesis-rag-labour-law）是 RAG **流水线**——改写→检索→门控→生成，控制流写死在代码里，确定性优先；本项目把同一领域任务 **Agent 化**——由模型自主决定调用哪些工具、调用几次、是否追问，对应论文"未来工作"的 Agentic RAG 方向。
## 项目结构

```
labour-agent-demo/
├── labour_agent.py        # v1：手写 ReAct 循环 + Function Calling + 4 工具（零框架依赖）
├── langgraph_agent.py     # v2：LangGraph StateGraph 编排（工具实现直接复用 v1）
├── agent_hitl.py          # v3：多轮记忆（Sqlite 检查点）+ 人在环审批（interrupt）
├── observability.py       # v4：可观测性：本地追踪 + token/成本核算（可切换 LangSmith）
├── agent_eval.py          # 评测：11 案 × 2 架构，客观指标自动打分（测试集内置于此文件）
├── selftest.py            # 环境自检：一条命令确认依赖/配置/API/模块是否就绪
├── TESTING.md             # 本地测试指南（分步测试流程、演示脚本、常见问题）
├── eval_results.json      # 评测明细输出（含双方完整答案，可复核）
└── README.md
```

## 一、v1 手写循环版（`labour_agent.py`）

**核心循环**：模型思考 → 决定调用工具 → 工具返回 → 模型再思考，直到信息足够给出最终回答。

**4 个工具**：

| 工具 | 职责 | 设计要点 |
|---|---|---|
| `search_law` | 法条检索（内置 11 条真实条文摘录） | 工具描述写死"严禁编造条文号"，从机制上防幻觉 |
| `calculate_compensation` | 按第 47/87/40 条算 N / N+1 / 2N | 金额由 Python 计算：可复现、可审计（**不是**为了防 LLM 算错，见评测发现） |
| `check_arbitration_deadline` | 仲裁时效（第 27 条及例外） | 存续期间不受 1 年限制的例外要准确区分 |
| `ask_user` | 反问澄清 | Human-in-the-loop，关键数字不猜 |

**护栏**：`MAX_STEPS = 8` 循环步数上限，防无限调用工具。

## 二、v2 LangGraph 版（`langgraph_agent.py`）

```
        ┌─────────────────────────────┐
        │ llm 节点：模型思考并决策     │
        └───┬─────────────────────┬───┘
       有 tool_calls          无 tool_calls
            │                     │
            ▼                     ▼
      ┌───────────┐             END
      │ tools 节点 │
      └─────┬─────┘
            └──────────→ 回 llm 节点
```

- `StateGraph` + `add_messages` 归约器管理消息状态；`ToolNode` 预置节点自动执行工具调用
- 条件边 `should_continue` 只负责**路由**（有 tool_calls 就去 tools，否则结束），**决定调用什么工具的是模型**
- 护栏换成 `recursion_limit=19`（约 8 轮），超限抛 `GraphRecursionError`
- **工具实现直接 `import` 自 v1**——演示"编排层换框架，业务工具零改动"的分层设计
- 实测可见 LangGraph 会**并行执行**同一轮的多个工具调用（如同时调时效查询 + 法条检索），手写版是串行

## 三、v3 多轮记忆 + 人在环审批（`agent_hitl.py`）

在 v2 编排之上加两个**生产级能力**，都是落地生产环境时的关键能力。

### 1. 多轮记忆（持久化状态，跨进程）

`graph.compile(checkpointer=SqliteSaver(conn))` + `config={"configurable": {"thread_id": ...}}`：
整个会话状态（全部消息 + 中间状态）落盘到 `agent_memory.sqlite`，按 thread 隔离。

**验证过的效果**——关掉程序重开，Agent 仍记得案情：

```bash
# 第一次：报案情，生成文书
.venv/Scripts/python agent_hitl.py --thread demo-01 --demo
# 第二次（全新进程）：不重述案情直接问
.venv/Scripts/python agent_hitl.py --thread demo-01 --question "我的工龄是几年？月工资多少？被申请人是谁？"
```

实测第二次回答（**未经任何重述**）：

> 根据我们前面的沟通，已记录的信息如下：
> 1. **被申请人（公司）**：某某科技有限公司
> 2. **工龄**：2年半（2.5 年）
> 3. **月工资**：离职前12个月平均月工资 **9,000 元**
> 基于以上信息，我已为您计算出违法解除劳动合同赔偿金为 **54,000 元**，并生成了仲裁申请书。

> 为什么不用 `MemorySaver`：它只存在内存里，进程一退记忆就没了，演示不出"跨会话"。Sqlite 才有真实持久化的意义（生产环境可换 Postgres/Redis 检查点）。

### 2. 人在环审批（Human-in-the-loop）

**为什么需要**：生成《劳动仲裁申请书》是高风险动作——用户可能直接拿去提交仲裁委。这类动作不能让模型自主执行，必须人工把关。

```python
def review_draft(state):
    decision = interrupt({          # 挂起整张图，把决定权交给人类
        "action": SENSITIVE_TOOL,
        "message": "Agent 准备生成正式《劳动仲裁申请书》，请核对要素后批准",
        "draft": state["pending_draft"]["args"],
    })
    ...
```

流程与实测（两条路径都验证过）：

| 人类决定 | 图的走向 | 实测结果 |
|---|---|---|
| **批准** | 恢复 → 执行工具 → 生成文书 | ✅ 生成带完整结构的《劳动人事争议仲裁申请书》 |
| **否决 + 修改意见** | 恢复 → 带意见回 llm 重做 | ✅ Agent 重新检索《劳动合同法》第 47 条补强计算依据，二次审批后生成修订版 |

**实现里最容易踩的两个坑（都处理了）**：

1. **否决后必须补工具回执**：历史里若留下"调用过但无 ToolMessage 回应"的 `tool_call`，再调 LLM 会被 API 直接拒绝。所以否决时要为整批 `tool_call_id` 补一条"操作被用户否决，未执行"的 `ToolMessage`。
2. **`interrupt()` 恢复后节点从头重跑**：所以 interrupt 之前的代码必须幂等——不能有副作用（写文件、发请求）。

## 四、可观测性：本地追踪 + 成本核算（`observability.py`）

生产环境的 Agent 必须能回答三个问题：**花了多少钱、慢在哪一步、哪次调用失败了**。

`observability.py` 提供 `TraceCollector`（继承 `BaseCallbackHandler`），**零外部依赖、零账号**，
挂进图调用的 `config["callbacks"]` 即可采集。
（当前只有 v3 接好了开关；v2 需给 `run_turn` 加 callbacks 参数，v1 走原生 OpenAI SDK、不经过
LangChain 回调链，需要自行改造才能挂载。）

```bash
.venv/Scripts/python agent_hitl.py --thread demo --trace --question "公司拖欠我3年工资还能要回来吗？"
```

实测输出（真实数据；节选——完整报告还会多打印「工具耗时 Top3」与单价说明两行）：

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  工具调用     2 次   check_arbitration_deadline×1、ask_user×1

```

**采集到的关键信息：**

| 维度 | 内容 |
|---|---|
| LLM | 调用次数、每次耗时、平均/最慢、输入输出 token（**区分缓存命中与未命中**） |
| 工具 | 每次调用的工具名、耗时、返回长度、异常 |
| 成本 | 按时段与缓存命中率核算，单价可被环境变量覆盖 |
| 汇总 | 控制台报告 + 追加写入 `trace_log.jsonl`（便于离线分析） |

**为什么自己做而不只依赖 LangSmith：**

1. **零账号零外网**：本地即可用，离线/内网演示不受限（也是这个 demo 能直接跑起来的前提）
2. **成本口径可控**：DeepSeek 缓存命中价只有未命中的 1/120（0.025 vs 3.0），不区分命中率的成本核算会严重高估；上面的实测就显示 90% 输入走了缓存
3. **理解了回调机制，接平台只是多一个 callback**——本地采到的指标口径定义清楚了，才知道该看平台的哪个面板

**接入 LangSmith（可选，两行配置）**：把 `.env.example` 里的 `LANGSMITH_TRACING` / `LANGSMITH_API_KEY`
取消注释即可——LangChain 会自动开启云端追踪，与本地 `TraceCollector` **同时生效互不冲突**
（因为显式 callback 与全局自动追踪是两条独立通道）。
注意两点：① 开启后追踪数据会上传云端（数据离开本机），自行权衡；② LangSmith 在境外需配 `HTTPS_PROXY`。

> 单价说明：`PRICE_TABLE` 是 2026-09 检索到的公开价目（元/百万 tokens），仅用于**成本量级估算**；
> 厂商会调价、也有峰谷分时计价，请以实际账单为准，可用 `LLM_PRICE_*` 环境变量覆盖。

## 五、评测：Agent 版 vs 流水线版（`agent_eval.py`）

**为什么不用 LLM-as-judge**：Agent 评测是行业公认难题（行为不确定、路径不唯一），而 LLM 评委本身不可靠。本评测全部用**可客观验证的指标**：

| 指标 | 定义 | 检验什么 |
|---|---|---|
| 工具召回率 | 该调的必调工具是否都调了 | 决策正确性（金额问题必须调计算工具） |
| 反问行为正确 | 信息不全该追问、信息齐全不该啰嗦 | Agent 专有能力（流水线结构上做不到） |
| 金额正确率 | 期望金额是否以"主张/计算"口吻出现（否定句、假设句不算） | 程序计算 vs LLM 心算 |
| 引用可验证率 | 引用的每个第X条能否回溯到知识库（兼容中文数字条号） | 防幻觉白名单机制 |

**公平性设置**：流水线版拿到与 Agent 版**相同的信息**（脚本把用户补充信息一次性喂给它），它的劣势不是信息更少，而是**无法边问边查**——只检索一次、不做程序化计算、无引用白名单约束。

**测试集覆盖**（11 案）：信息不全的违法辞退（应追问）、信息齐全的违法辞退（不应追问，检验过度提问）、拖欠工资时效、未签合同双倍工资、主动辞职、加班费、试用期辞退、N+1 计算、协商解除、知识边界（迷你库无工伤条例，检验是否编造条文号）、零头工龄算例（7年8个月，检验月数取整规则）。

## 六、评测结果（11 案 × 2 架构，2026-09-14 实测）

| 指标 | Agent 版 | 流水线版 | 说明 |
|---|---|---|---|
| 工具召回率 | **100%** | 73% | 流水线只有检索一步，无工具选择能力（结构上限） |
| 反问行为正确 | **80%** | 60% | 流水线架构上不具备追问能力 |
| 金额正确率 | 100% | 100% | ⚠️ 见下方"发现二" |
| 引用可验证率 | **93%** | 84% | 引用能否回溯到知识库 |
| 关键条文命中 | **100%** | 90% | 参考答案应出现的关键条文 |
| 平均工具调用次数 | 4.1 次（2–7） | 1 次 | Agent 的结构性成本：LLM 往返次数更多 |
| 平均耗时 | 28.6s | 59.5s | 单次采样受模型服务波动影响大，不宜直接对比 |

### 评测过程本身的三个发现

**发现一：打分器有 bug，修正后结论反转。**
首轮评测显示"金额正确率 Agent 100% vs 流水线 67%"，结论看似漂亮。但核对明细发现是**打分器的缺陷**：模型把条号写成中文数字"第**八十七**条"、金额写成"**6万**元"，而我的正则只认阿拉伯数字和纯数字，导致引用和金额都没被识别——流水线被误判为"算错"。

修正打分口径（增加中文数字与"万"的解析）后重算，**金额正确率两边都是 100%**。这直接推翻了"不让 LLM 心算"的初始假设：**在本测试集的算例上，LLM 的心算并没有出错**，包括最难的零头工龄用例（7 年 8 个月 → 按 1 年计 → 8 个月 × 15000 × 2 = 240,000 元），流水线也完整推导正确。

> 教训：**评测指标本身必须先被验证**，否则会得出"数据支持的、但实际不存在"的结论。这也是为什么本评测坚持用可复核的客观指标而非 LLM 打分——出问题时至少能定位到具体是哪一行代码判错了。

**发现二：指标有语义边界，"不可验证的引用"≠"编造的引用"。**
C06（加班费）中，流水线引用《劳动法》第 44 条——**真实且法律上正确**，但不在本项目迷你知识库内，因此"引用可验证率"记为 0%。这暴露了该指标的真实含义：它衡量的是**可溯源性（能否回溯到知识库）**，而不是**正确性**。

> 结论：Agent 引用白名单机制的价值是"每条引用都能被审计"，而不是"保证答案一定对"。真实生产环境应把它当作**风险标记**而非**正确性分数**。

**发现三：修完第一个打分器 bug，独立审查又揪出第二个（漏抽引用）。**
后来对项目做了一轮独立代码审查，发现 `_extract_citations` 用位置断言 `(?<![》\s])` 去重，
把"换行/项目符号之后的裸条号"整条漏抽了（例如 markdown 列表里的 `- 第46条明确限定…`）。
漏抽只缩小分母，会**系统性高估**引用可验证率。改成"先把带法律名的引用整体摘除、再抽剩余裸条号"
之后：C09 由 66.7% 修正为 75%，Agent 平均由 92.4% → **93.2%**（表内已按新口径更新）；
顺带修掉两个当时没暴露的解析缺陷——中文数字"一百零七"会被算成 100、条号正则不含"千"。

> 同一个指标前后被修了两次，这恰好说明**"可自动验证"不等于"自动正确"**：
> 指标代码本身同样要被审查、要写单测，否则你会得到一组"看起来很客观"的错误数字。

后来又把两处**过松的判定**收紧（并逐案验证未造成数字漂移）：
金额正确率从"提及即通过"改为"必须以主张/计算口吻出现"——否定句（"不是 48000 元"）与
假设句（"理论上 N+1 是 22500 元，但本案不适用"）不再算对；零引用的正确拒答
（"本知识库未收录"）记 N/A 而非 0 分，不再拖低平均。这两处都由单测固定住（`test_units.py`）。

**其他真实观察（不美化）**：
- Agent 在 C08 上**过度追问**（该用例信息已齐全，仍追问"公司是否提前 30 天书面通知"——严格说这个追问对判断 N+1 是合理的，属于可争议用例）
- Agent 在 C10（知识库无工伤条例）上**连续检索 6 次**才放弃，耗时 41.6s——检索无果时存在无效重试，可用"同一查询重试上限"优化
- 无论哪一方，答案结尾都稳定输出免责声明，未见明显越界提供法律意见的情况

### 那程序化计算到底有没有价值？

有，但不是"防止算错简单题"，而是这三点——**这三条恰好是 prompt 做不到的**：
1. **可复现**：同一输入永远同一结果，不随模型版本/温度漂移
2. **可审计**：金额来自 `_calc_months()` 的确定性函数，出错能定位到具体一行规则
3. **规则可演进**：法条变化时改代码（如补上"社平工资 3 倍封顶"——当前实现只标注了该简化，未实现），不需要重新调 prompt 并祈祷模型学会

## 下一步可扩展

1. **多 Agent 分工**：检索 Agent + 计算 Agent + 文书生成 Agent 的 supervisor 编排
2. **记忆治理**：长对话的消息裁剪/摘要（避免历史无限增长撑爆上下文）、跨 thread 的用户画像
3. **接入真实检索**：把 `search_law` 换成论文项目的混合检索（BM25 + 向量 + 知识图谱），可直接复用于论文系统的 Agentic 升级
4. **评测补强**：给 `agent_eval.py` 也挂上 `TraceCollector`，把每案的 token 成本纳入评测报表
