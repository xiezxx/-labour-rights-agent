# 劳动维权咨询 Agent —— 作品集演示项目

面向 **AI Agent 应用开发**的完整演示：同一业务的 **三种架构对照**——手写 ReAct 循环版、LangGraph 编排版、流水线基线版，外加一套**可自动验证的 Agent 评测**。


## 项目结构

```
labour-agent-demo/
├── labour_agent.py        # v1：手写 ReAct 循环 + Function Calling + 4 工具（零框架依赖）
├── langgraph_agent.py     # v2：LangGraph StateGraph 编排（工具实现直接复用 v1）
├── agent_eval.py          # 评测：11 案 × 2 架构，客观指标自动打分（测试集内置于此文件）
├── eval_results.json      # 评测明细输出（含双方完整答案，可复核）
└── README.md
```

## 快速运行

```bash
python -m venv .venv
.venv/Scripts/pip install openai python-dotenv langgraph langchain-openai   # Windows
cp .env.example .env    # 填入 DeepSeek / OpenAI 兼容 API Key

.venv/Scripts/python labour_agent.py --demo           # v1 手写循环版，脚本演示
.venv/Scripts/python langgraph_agent.py --demo        # v2 LangGraph 版，脚本演示
.venv/Scripts/python agent_eval.py                    # 评测（11 案情 × 2 架构，约 10 分钟）
.venv/Scripts/python agent_eval.py --rescore          # 只重算指标，不调用 LLM（改打分口径时用）
.venv/Scripts/python agent_eval.py --case C01         # 单跑一个用例
```

去掉 `--demo` 即为交互模式，可多轮追问。

## 一、v1 手写循环版（`labour_agent.py`）

**核心循环**：模型思考 → 决定调用工具 → 工具返回 → 模型再思考，直到信息足够给出最终回答。

**4 个工具**：

| 工具 | 职责 | 设计要点 |
|---|---|---|
| `search_law` | 法条检索（内置 11 条真实条文摘录） | 工具描述写死"严禁编造条文号"，从机制上防幻觉 |
| `calculate_compensation` | 按第 47/87/40 条算 N / N+1 / 2N | 金额由 Python 计算：可复现、可审计（**不是**为了防 LLM 算错，见评测发现） |
| `check_arbitration_deadline` | 仲裁时效（第 27 条及例外） | 存续期间不受 1 年限制的例外要准确区分 |
| `ask_user` | 反问澄清 | Human-in-the-loop，关键数字不猜 |

**护栏**：`MAX_STEPS = 8` 循环步数上限，防无限调用工具。

## 二、v2 LangGraph 版（`langgraph_agent.py`）

```
        ┌─────────────────────────────┐
        │ llm 节点：模型思考并决策     │
        └───┬─────────────────────┬───┘
       有 tool_calls          无 tool_calls
            │                     │
            ▼                     ▼
      ┌───────────┐             END
      │ tools 节点 │
      └─────┬─────┘
            └──────────→ 回 llm 节点
```

- `StateGraph` + `add_messages` 归约器管理消息状态；`ToolNode` 预置节点自动执行工具调用
- 条件边 `should_continue` 只负责**路由**（有 tool_calls 就去 tools，否则结束），**决定调用什么工具的是模型**
- 护栏换成 `recursion_limit=19`（约 8 轮），超限抛 `GraphRecursionError`
- **工具实现直接 `import` 自 v1**——演示"编排层换框架，业务工具零改动"的分层设计
- 实测可见 LangGraph 会**并行执行**同一轮的多个工具调用（如同时调时效查询 + 法条检索），手写版是串行

## 三、评测：Agent 版 vs 流水线版（`agent_eval.py`）

**为什么不用 LLM-as-judge**：Agent 评测是行业公认难题（行为不确定、路径不唯一），而 LLM 评委本身不可靠。本评测全部用**可客观验证的指标**：

| 指标 | 定义 | 检验什么 |
|---|---|---|
| 工具召回率 | 该调的必调工具是否都调了 | 决策正确性（金额问题必须调计算工具） |
| 反问行为正确 | 信息不全该追问、信息齐全不该啰嗦 | Agent 专有能力（流水线结构上做不到） |
| 金额正确率 | 答案金额是否等于程序计算值（±1 元） | 程序计算 vs LLM 心算 |
| 引用可验证率 | 引用的每个第X条是否出现在本轮检索结果中 | 防幻觉白名单机制 |

**公平性设置**：流水线版拿到与 Agent 版**相同的信息**（脚本把用户补充信息一次性喂给它），它的劣势不是信息更少，而是**无法边问边查**——只检索一次、不做程序化计算、无引用白名单约束。

**测试集覆盖**（10 案）：信息不全的违法辞退（应追问）、信息齐全的违法辞退（不应追问，检验过度提问）、拖欠工资时效、未签合同双倍工资、主动辞职、加班费、试用期辞退、N+1 计算、协商解除、知识边界（迷你库无工伤条例，检验是否编造条文号）。

## 四、评测结果（11 案 × 2 架构，2026-09-14 实测）

| 指标 | Agent 版 | 流水线版 | 说明 |
|---|---|---|---|
| 工具召回率 | **100%** | 73% | 流水线只有检索一步，无工具选择能力（结构上限） |
| 反问行为正确 | **80%** | 60% | 流水线架构上不具备追问能力 |
| 金额正确率 | 100% | 100% | ⚠️ 见下方"发现二" |
| 引用可验证率 | **92%** | 84% | 引用能否回溯到知识库 |
| 关键条文命中 | **100%** | 90% | 参考答案应出现的关键条文 |
| 平均工具调用次数 | 4.1 次（2–7） | 1 次 | Agent 的结构性成本：LLM 往返次数更多 |
| 平均耗时 | 28.6s | 59.5s | 单次采样受模型服务波动影响大，不宜直接对比 |

### 评测过程本身的两个发现（演示重点）

**发现一：打分器有 bug，修正后结论反转。**
首轮评测显示"金额正确率 Agent 100% vs 流水线 67%"，结论看似漂亮。但核对明细发现是**打分器的缺陷**：模型把条号写成中文数字"第**八十七**条"、金额写成"**6万**元"，而我的正则只认阿拉伯数字和纯数字，导致引用和金额都没被识别——流水线被误判为"算错"。

修正打分口径（增加中文数字与"万"的解析）后重算，**金额正确率两边都是 100%**。这直接推翻了"不让 LLM 心算"的初始假设：**在本测试集的算例上，LLM 的心算并没有出错**，包括最难的零头工龄用例（7 年 8 个月 → 按 1 年计 → 8 个月 × 15000 × 2 = 240,000 元），流水线也完整推导正确。

> 教训：**评测指标本身必须先被验证**，否则会得出"数据支持的、但实际不存在"的结论。这也是为什么本评测坚持用可复核的客观指标而非 LLM 打分——出问题时至少能定位到具体是哪一行代码判错了。

**发现二：指标有语义边界，"不可验证的引用"≠"编造的引用"。**
C06（加班费）中，流水线引用《劳动法》第 44 条——**真实且法律上正确**，但不在本项目迷你知识库内，因此"引用可验证率"记为 0%。这暴露了该指标的真实含义：它衡量的是**可溯源性（能否回溯到知识库）**，而不是**正确性**。

> 结论：Agent 引用白名单机制的价值是"每条引用都能被审计"，而不是"保证答案一定对"。真实生产环境应把它当作**风险标记**而非**正确性分数**。

**其他真实观察（不美化）**：
- Agent 在 C08 上**过度追问**（该用例信息已齐全，仍追问"公司是否提前 30 天书面通知"——严格说这个追问对判断 N+1 是合理的，属于可争议用例）
- Agent 在 C10（知识库无工伤条例）上**连续检索 6 次**才放弃，耗时 41.6s——检索无果时存在无效重试，可用"同一查询重试上限"优化
- 无论哪一方，答案结尾都稳定输出免责声明，未见明显越界提供法律意见的情况

### 那程序化计算到底有没有价值？

有，但不是"防止算错简单题"，而是这三点——**这三条恰好是 prompt 做不到的**：
1. **可复现**：同一输入永远同一结果，不随模型版本/温度漂移
2. **可审计**：金额来自 `_calc_months()` 的确定性函数，出错能定位到具体一行规则
3. **规则可演进**：法条变化时改代码（如补上"社平工资 3 倍封顶"——当前实现只标注了该简化，未实现），不需要重新调 prompt 并祈祷模型学会




## 下一步可扩展

1. **多轮记忆**：跨会话的案情状态持久化（LangGraph checkpointer，`MemorySaver`/`SqliteSaver`）
2. **多 Agent 分工**：检索 Agent + 计算 Agent + 文书生成 Agent 的 supervisor 编排
3. **人在环审批**：生成仲裁申请书这类"对外动作"前加人工确认节点（LangGraph `interrupt`）
4. **接入真实检索**：把 `search_law` 换成论文项目的混合检索（BM25 + 向量 + 知识图谱），可直接复用于论文系统的 Agentic 升级

## 说明

- 迷你法条库为 11 条真实条文摘录，检索为演示级轻量实现（字符二元组重叠度评分），生产环境应替换为论文项目的混合检索
- 所有法律回答仅供参考，不构成正式法律意见
